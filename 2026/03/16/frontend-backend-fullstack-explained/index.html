欠同事一週的文章：前端、後端與全端到底是什麼？

"""

這篇文章，我其實欠公司一位同仁很久了。

本來只是很單純地說：「好，我再找時間跟你解釋什麼是前端、什麼是後端、什麼又叫全端。」結果這個「找時間」，一找就是一個禮拜。身為工程師，欠技術債已經夠可怕了，連文章債都欠，實在有點不好意思。

所以今天就來把這篇補上，而且盡量用最白話、最好理解的方式來說明。這篇不是要寫成教科書，也不是要端出一堆艱澀名詞把大家嚇跑，而是希望讓沒有技術背景的人，看完也能大概知道：

  • 前端是在做什麼
  • 後端是在做什麼
  • 全端又為什麼常常被講得很神

先講結論：你看到的，通常是前端；你看不到的，很多是後端

如果要用一句話先快速區分，我會這樣說：

跟畫面、瀏覽器、使用者操作直接有關的，多半是前端。

藏在伺服器、資料庫、商業邏輯後面的，多半是後端。

這樣講當然不是百分之百精準，但對入門理解非常夠用了。

很多人一聽到「前端」，直覺就是「喔，就是畫畫面的人」。這樣理解不能說錯，但其實只對了一半。因為前端除了處理「看得到的畫面」，也要處理很多「你看不到，但發生在瀏覽器裡的事情」。

而後端呢，通常更神秘一點，因為它大多待在伺服器裡默默工作。你平常不會直接看到它，但網站能不能正常運作、資料對不對、登入有沒有成功，很多都是後端在撐場。

什麼是前端？

前端，簡單來說，就是直接面對使用者的那一端。

只要是你打開網站後，在瀏覽器裡看到、點到、輸入到、互動到的東西，大多都屬於前端的範圍。像是：

  • 首頁長什麼樣子
  • 按鈕放哪裡
  • 表單怎麼輸入
  • 點擊之後畫面怎麼切換
  • 手機版畫面會不會跑版
  • 資料拿回來之後怎麼顯示在畫面上

這些都很直觀，因為「看得到」。

如果你把整個網站想成一間正在運作的店，前端有點像站在第一線接待客人的那個人。客人看到的第一印象、能不能順利互動、操作時會不會覺得舒服，很多都跟這個位置有關。

但前端有趣的地方就在於，它不只管看得到的部分，也會處理很多瀏覽器裡「看不到」的事情。

例如：為什麼你登入一次，瀏覽器就像認得你了？

你有沒有遇過這種情況？

你進一個網站，按下登入，輸入帳號密碼，成功登入後就可以開始使用。然後你重新整理頁面，咦，還是登入狀態。甚至你把分頁關掉，過一段時間再回來，有時候網站還記得你。

很多人會覺得這很神奇，好像瀏覽器突然有了記憶。

其實這背後沒有魔法，只有工程師。

通常流程會是這樣：

  1. 你在前端畫面輸入帳號密碼。
  2. 前端把這些資料送去後端。
  3. 後端驗證帳號密碼是不是正確。
  4. 如果正確，後端會回傳一個能代表「你已經登入」的資訊。
  5. 前端再把這個資訊暫存在瀏覽器裡。

這個暫存的位置，可能是 Cookie、Local Storage、Session Storage，或者其他瀏覽器端的機制。名字先不用急著背，入門先知道一件事就好：

瀏覽器之所以像是記得你，是因為前端把後端驗證後回傳的資訊，暫時存放在瀏覽器裡。

如果把這件事畫成一個小劇場，大概就像櫃台確認完你的身份之後，交給瀏覽器一張通行證，讓它下次看到你時知道：「喔，這位我認得。」

所以你看，前端不是只有畫面漂亮不漂亮而已，它還要負責管理很多使用者操作流程，以及瀏覽器內部的狀態。

也就是說，前端工程師不是只會排版。很多時候他還得處理：

  • 登入狀態怎麼保存
  • API 拿回來的資料怎麼整理
  • 按下按鈕後要不要跳提示
  • 資料還沒回來時要不要先顯示 loading
  • 權限不對時要不要擋畫面

這些事情雖然使用者不一定會注意到，但只要沒處理好，網站馬上就會很有個性，而且通常是那種讓人火大的個性。

什麼是後端？

如果說前端是站在第一線，直接面對使用者，那後端就是在後方撐住整個系統的那一群。

後端比較常見可以分成幾個部分：

  • Server
  • Database
  • 後端程式碼

因為這些東西大多不直接展示給使用者看，所以對非工程背景的人來說，後端常常會有一種神秘感。明明看不到，但它又真的存在，而且出了問題時，整個網站就會像失去靈魂一樣。

後端可以想像成什麼？

你可以想像一下，你現在正在用的這台電腦，其實也可以拿來當一台後端 Server。

假設今天你在這台電腦上：

  • 架了一個資料庫
  • 寫了一套 Web Server
  • 把後端程式跑起來

那這台電腦就可以扮演後端的角色。

前端只要知道這台機器提供哪些 API，就可以透過網路去跟它要資料、送資料、更新資料。

例如：

  • 我要登入，請幫我驗證帳密
  • 我要看會員資料，請把資料給我
  • 我要查商品列表，請把商品資料吐給我
  • 我要送出訂單，請幫我寫進資料庫

這些事情，通常就是後端在處理。

後端到底在忙什麼？

後端不是單純「把資料拿出來」而已，它常常還要做很多判斷與保護，例如：

  • 這個人有沒有登入
  • 這個人有沒有權限看這份資料
  • 傳進來的參數是不是合法
  • 資料要存到哪一張資料表
  • 如果資料衝突了該怎麼辦
  • 回傳給前端的格式要長什麼樣子

也就是說，後端常常是在處理規則、邏輯、資料與安全性。

如果把網站比喻成一家餐廳，前端像是外場，負責接待客人、送菜單、讓客人知道該怎麼點餐；後端就像內場廚房，負責真的把菜做出來、確認材料夠不夠、訂單有沒有問題。

這也是我很喜歡拿來解釋後端的比喻，因為它不只是神秘地待在後面，而是真的有一群人在忙著把規則、資料和流程穩穩接住。

你在外面看到餐點順順地送上桌，背後通常都不是奇蹟，而是一整套流程在運作。

前端跟後端怎麼合作？

講到這裡，通常下一個問題就是：

「那前端跟後端是怎麼溝通的？」

答案就是：透過 API。

你可以先把 API 想成一個「雙方約定好的溝通窗口」。

前端需要什麼資料，就去呼叫後端提供的 API。後端收到請求後，去做該做的事，再把結果回傳給前端。前端最後再把這些資料渲染到畫面上。

所以一個很常見的流程就是：

  1. 使用者在前端點了一個按鈕。
  2. 前端呼叫後端 API。
  3. 後端去查資料庫或做邏輯處理。
  4. 後端把結果用固定格式回傳。
  5. 前端收到後，把資料顯示在畫面上。

例如你打開一個訂單頁面：

  • 前端說：「我要訂單列表。」
  • 後端說：「好，我去資料庫查一下。」
  • 查完後，後端把 JSON 資料回傳。
  • 前端收到後，把它排成表格讓你看。

整個過程如果配合得好，使用者就會覺得網站很順。

如果配合得不好，就會出現各種經典場面，例如：

  • 前端說要 user_id，後端回 uid
  • 前端以為回傳的是陣列，結果後端回一個物件
  • 前端以為成功時會回 code: 200，結果後端回的是 status: ok

最後大家就會在會議室裡深情對望，然後開始說：「我以為你那邊會改。」

所以，API 溝通真的不是「有串到就好」，而是前後端要先講好規格。

API 規格，真的是前後端先講好的

這件事我很想特別講一下，因為很多剛接觸的人會以為 API 好像是後端自己寫一寫，前端再想辦法猜。

其實不是。

正常的開發流程裡，前後端通常會先約定好很多事情，例如：

  • 要用什麼 HTTP 方法，例如 GET、POST、PUT、DELETE
  • 請求要帶哪些參數
  • 參數名稱叫什麼
  • 回傳資料格式長什麼樣子
  • 成功時怎麼回
  • 失敗時怎麼回
  • 錯誤訊息要怎麼表示

這些規則如果沒有先談好，開發過程就很容易變成大型猜謎現場。

前端會猜：「你這個欄位是不是可能為空？」

後端會猜：「你那邊應該知道這個欄位不是每次都會回吧？」

猜到最後，專案進度就會像壞掉的跑步機，看起來很努力，實際上沒往前多少。

所以前後端的合作，除了寫程式本身，溝通規格也是很重要的一部分。

那什麼是全端？

講完前端與後端，全端就好理解很多了。

全端工程師，簡單來說，就是前端跟後端都能處理的人。

如果把場景再拉大一點，全端有點像那種不只會站前場，也敢走進後場，甚至能幫忙把兩邊節奏對起來的人。

他可能可以：

  • 寫前端畫面
  • 串接 API
  • 寫後端邏輯
  • 設計資料庫
  • 處理部署與基本維運

也就是從使用者打開網站，到資料真的被存進資料庫，中間整條鏈路他都大概看得懂，甚至都能動手做。

全端是不是等於什麼都要超強？

這裡也要幫全端平反一下。

很多人聽到全端，會以為那是一種神級生物，前端、後端、資料庫、Server、CI/CD、資安、UI/UX 全部點滿，晚上還順便修一下公司印表機。

現實通常不是這樣。

比較務實的理解是：

全端不是每一科都一定要滿分，而是你對整體流程都有概念，也能跨區域解問題。

有些全端偏前端，有些全端偏後端，這都很正常。

重點是，當一個功能要從畫面一路接到資料庫時，他不會只看自己那一小塊，而是能理解整體怎麼串起來。

這也是為什麼很多公司喜歡找全端，因為溝通成本通常會低一些，推進事情也更快一些。

當然，代價就是腦容量常常不夠用，昨天還在切版，今天就在查 SQL，明天可能又在看 Nginx 設定。某種程度上，全端工程師的日常，就是一種很有技術含量的精神分裂。

一個最簡單的例子：登入功能，到底誰在做什麼？

如果我們用「登入」這件事來拆開看，其實前端、後端、全端的分工會非常清楚。

前端負責的部分

  • 做出登入頁面
  • 讓使用者可以輸入帳號密碼
  • 按下登入按鈕後把資料送出去
  • 收到後端回應後，決定要跳成功、失敗，還是顯示錯誤訊息
  • 把登入成功後的資訊暫存在瀏覽器

後端負責的部分

  • 接收前端送來的帳號密碼
  • 驗證帳號密碼正不正確
  • 去資料庫查詢這個使用者
  • 判斷帳號狀態是否正常
  • 驗證成功後回傳登入憑證或相關資訊

全端會怎麼看這件事？

全端通常會從頭到尾一起看：

  • 前端頁面怎麼設計比較順
  • API 路由怎麼命名比較合理
  • 回傳格式怎麼定比較好串
  • Token 要怎麼存比較安全
  • 資料表該怎麼設計比較不容易出問題

所以全端的價值，很多時候不是「一個人做全部比較帥」，而是「一個人比較容易看懂整個系統怎麼運作」。

我自己的理解，總結成一句話

如果你今天只是想先快速抓住概念，我會這樣整理：

  • 前端：凡是跟畫面、瀏覽器、使用者互動，以及瀏覽器端狀態管理有關的，多半都算前端。
  • 後端：凡是跟 Server、資料庫、商業邏輯、驗證、資料處理有關的，多半都算後端。
  • 全端：能把前端跟後端串起來，理解整條流程，並能跨兩邊處理問題的人。

這個說法不是學術定義，但對大部分想入門的人來說，我覺得很夠用了。

結語：別再把工程師都叫做「會修電腦的」

寫到這裡，希望這位被我拖稿一週的同仁，看到這篇之後可以原諒我。

也希望其他看到這篇文章的朋友，以後在聽到前端、後端、全端時，不會再覺得那是一堆很遠很硬的名詞。

它其實沒有那麼玄。

前端，就是讓你看得到、點得到、用得到。

後端，就是讓這一切真的能運作，真的有資料，真的有邏輯。

全端，就是兩邊都懂，負責把整台車從方向盤一路接到引擎。

而如果再往上多看一層，還會碰到 Infra。

所謂的 Infra，其實就是 Infrastructure，也就是系統運作的基礎設施。白話一點講，就是除了前端、後端程式本身之外，還要去處理「這整個系統到底要跑在哪裡、怎麼連、怎麼部署、怎麼撐住」這些事情。

如果前端像舞台上的演員，後端像幕後實際把內容做出來的團隊，那 Infra 就更像是整個舞台後勤與總控室。觀眾不一定會看到他們，但燈光、線路、機器、節奏，只要哪裡出問題，整場演出就會立刻露餡。

例如：

  • Server 要怎麼配置
  • Database 要怎麼部署
  • Nginx 或 Web Server 要怎麼設定
  • Docker 要怎麼包服務
  • 網路怎麼通
  • Port 怎麼開
  • 反向代理怎麼設計
  • 整體系統架構要怎麼規劃才比較穩

這些東西，通常又會比單純的後端再多跨出去一點。因為它已經不只是寫商業邏輯，而是開始思考整個服務怎麼活下來、怎麼順順地跑、怎麼讓前後端可以穩定合作。

坦白說，這一塊也剛好是我自己一直很有興趣、也持續在累積的能力方向。

我雖然是後端出身，但實際做的事情不只後端。從前端串接、後端設計，到部署、網路與 Infra，我都很有興趣，也一直在實戰中慢慢把這些能力補齊。

其實這個部落格本身，就是一個很實際的例子。因為如果我只是單純寫文章，事情不會走到這一步；但當我想把它真的做成一個可以對外展示、也能持續運作的網站時，我就得碰前端、碰後端，甚至得自己去處理一些 Infra 的事情。像是這個網站的呈現本身需要前端調整，而我之前也另外架了一個自己的 API 來做頁面計數，這些都不是只懂單一技術面向就能完成的。

所以如果要用一句話形容我自己，我會說：

我不是只看單一技術面向的人，而是習慣從前端、後端一路看到 Infra 與整體系統的人。

畢竟現在很多問題，真的不是只會寫 API 或只會切版就能解決。你常常會遇到的情況是：程式明明寫好了，但部署不起來；服務明明有跑，但網路不通；功能明明正常，但整體架構一大就開始出現效能或維運問題。

而能同時掌握前端、後端、Infra、網路與系統架構的人，在這種時候就會特別有價值。因為他看到的不只是單一功能，而是整個系統如何從 0 到 1 被建立起來，怎麼部署、怎麼連線、怎麼穩定運作，最後怎麼真的活著。

尤其到了 AI 時代，我自己反而越來越覺得，真正能把 AI 用好的人，往往不是只會丟 prompt 的人，而是能理解整個系統架構的人。因為你最後會碰到的，從來都不只是模型本身，而是前端怎麼互動、後端怎麼串接、資料怎麼流動、服務怎麼部署、權限怎麼控、成本怎麼算、整體系統怎麼穩定地跑。

所以某種程度上，越是 AI 時代，越能看出「懂整體架構」這件事的價值。因為你不是只把一個功能做出來而已，而是要真的把它放進現實世界裡，讓它可以被使用、被維護，也能長期活下去。

如果你對這種「從 0 到 1 把一個服務真正做出來」的過程有興趣，也可以再看看我之前寫的另一篇文章：一個計數器API的誕生：看似簡單卻暗藏玄機的 Side Project。那篇就是在分享，我怎麼從雲端主機、Docker、Nginx、DNS、SSL、資料庫，一路把一個 API 真的建起來。

至於工程師是不是都會修電腦？

嗯……這個問題就跟你問廚師會不會修瓦斯爐一樣，有些人會，但真的不是職稱上的必修科目。

At first, it was just a simple promise: “Sure, I will find some time to explain what frontend is, what backend is, and what full-stack means.” But that “find some time” turned into a whole week. As an engineer, technical debt is already scary enough. Owing article debt too feels a little embarrassing.

So today, I am finally making up for it. I will explain it in the plainest and easiest-to-understand way I can. This article is not meant to be a textbook, nor is it meant to throw difficult terms at people and scare them away. I simply hope that even readers without a technical background can finish it and roughly understand:

  • What frontend does
  • What backend does
  • Why full-stack is often made to sound so impressive

The Quick Answer: What You See Is Usually Frontend; Much of What You Do Not See Is Backend

If I had to quickly separate them in one sentence, I would say this:

Anything directly related to the screen, browser, and user interaction is usually frontend.

Anything hidden behind servers, databases, and business logic is usually backend.

This is not 100% precise, of course, but it is more than enough for an introductory understanding.

When many people hear “frontend,” their instinct is: “Oh, the person who makes the screen.” That is not wrong, but it is only half right. Frontend handles the visible interface, but it also handles many things you do not see that happen inside the browser.

Backend is usually more mysterious because it mostly works silently on servers. You do not normally see it directly, but whether a website works properly, whether data is correct, and whether login succeeds are often supported by the backend.

What Is Frontend?

Simply put, frontend is the side that directly faces the user.

Anything you see, click, type into, or interact with in the browser after opening a website usually belongs to frontend. For example:

  • What the homepage looks like
  • Where buttons are placed
  • How forms are entered
  • How the screen changes after a click
  • Whether the mobile layout breaks
  • How returned data is displayed on the page

These things are intuitive because you can see them.

If you imagine a website as a running store, frontend is like the person standing at the front line greeting customers. The customer’s first impression, whether they can interact smoothly, and whether the experience feels comfortable are all related to this role.

But the interesting thing about frontend is that it does not only manage what you can see. It also handles many invisible things inside the browser.

For Example: Why Does the Browser Seem to Recognize You After You Log In Once?

Have you ever experienced this?

You enter a website, click login, type your account and password, and successfully sign in. Then you refresh the page, and you are still logged in. Sometimes you even close the tab, come back later, and the website still remembers you.

Many people feel this is magical, as if the browser suddenly gained memory.

There is no magic behind it. Only engineers.

The usual flow is:

  1. You type your account and password on the frontend page.
  2. The frontend sends that data to the backend.
  3. The backend verifies whether the account and password are correct.
  4. If they are correct, the backend returns information representing that “you are logged in.”
  5. The frontend temporarily stores that information in the browser.

That temporary storage location may be Cookie, Local Storage, Session Storage, or another browser-side mechanism. You do not need to memorize the names yet. For beginners, just remember one thing:

The browser seems to remember you because the frontend temporarily stores the information returned by the backend after verification inside the browser.

If we turn this into a small scene, it is like the front desk confirming your identity and then handing the browser a pass, so next time it sees you, it knows: “Oh, I recognize this person.”

So frontend is not only about whether the page looks pretty. It also manages many user workflows and browser-side states.

In other words, frontend engineers do more than layout. Many times, they also handle:

  • How login state is stored
  • How API data is organized after it comes back
  • Whether to show a prompt after a button is clicked
  • Whether to show loading before data returns
  • Whether to block a screen when permissions are wrong

Users may not always notice these things, but if they are handled badly, the website immediately develops a personality, usually the kind that makes people angry.

What Is Backend?

If frontend stands at the front line facing users, backend is the group behind the scenes that supports the whole system.

Backend commonly includes several parts:

  • Server
  • Database
  • Backend code

Because these things are mostly not shown directly to users, backend often feels mysterious to people without an engineering background. You cannot see it clearly, but it definitely exists. When it breaks, the whole website can feel like it has lost its soul.

What Can Backend Be Compared To?

You can imagine that the computer you are using right now could also become a backend Server.

Suppose that on this computer, you:

  • Set up a database
  • Write a Web Server
  • Run the backend program

Then this computer can play the backend role.

As long as the frontend knows which APIs this machine provides, it can request data, send data, and update data through the network.

For example:

  • I want to log in. Please verify my account and password.
  • I want to view member information. Please give me the data.
  • I want to search the product list. Please return product data.
  • I want to submit an order. Please write it into the database.

These are usually handled by the backend.

What Is Backend Busy With?

Backend is not just “taking data out.” It often makes many judgments and protections, such as:

  • Is this person logged in?
  • Does this person have permission to view this data?
  • Are the incoming parameters valid?
  • Which database table should the data be stored in?
  • What should happen if data conflicts?
  • What should the response format look like for the frontend?

In other words, backend often handles rules, logic, data, and security.

If a website is a restaurant, frontend is the dining area staff who greets customers, provides menus, and helps them know how to order. Backend is the kitchen team that actually cooks the food, checks whether ingredients are enough, and makes sure orders are correct.

This is one of my favorite metaphors for backend because it is not just mysteriously hiding in the back. It is a group of people keeping rules, data, and processes steady.

When you see dishes smoothly arrive at the table, it is usually not a miracle. It is an entire workflow operating behind the scenes.

How Do Frontend and Backend Work Together?

At this point, the next question is usually: “How do frontend and backend communicate?”

The answer is: through APIs.

You can think of an API as a communication window agreed upon by both sides.

When frontend needs data, it calls an API provided by the backend. The backend receives the request, does what it needs to do, and returns the result to the frontend. The frontend then renders that data on the screen.

A common flow looks like this:

  1. The user clicks a button on the frontend.
  2. The frontend calls a backend API.
  3. The backend queries the database or processes logic.
  4. The backend returns the result in a fixed format.
  5. The frontend receives the data and displays it on the page.

For example, when you open an order page:

  • Frontend says: “I need the order list.”
  • Backend says: “Okay, I will query the database.”
  • After querying, backend returns JSON data.
  • Frontend receives it and displays it as a table.

If this coordination works well, users feel the website is smooth.

If it does not work well, classic scenes appear:

  • Frontend asks for user_id, but backend returns uid
  • Frontend expects an array, but backend returns an object
  • Frontend expects success to return code: 200, but backend returns status: ok

Then everyone ends up staring at each other in the meeting room and saying, “I thought your side would change it.”

So API communication is not just about “it connects.” Frontend and backend must agree on the specification first.

API Specifications Are Really Agreed on by Frontend and Backend First

I especially want to mention this because many beginners think APIs are something backend writes by itself and frontend later guesses.

That is not how it should work.

In a normal development process, frontend and backend usually agree on many things first, such as:

  • Which HTTP method to use, such as GET, POST, PUT, or DELETE
  • Which parameters the request should carry
  • What the parameter names are
  • What the response data format looks like
  • What success responses look like
  • What failure responses look like
  • How error messages are represented

If these rules are not discussed first, development easily becomes a large guessing game.

Frontend guesses: “Can this field be null?”

Backend guesses: “Your side should know this field does not always return, right?”

After enough guessing, project progress becomes like a broken treadmill: it looks busy, but it does not move forward much.

So frontend-backend collaboration is not only about writing code. Communicating specifications is also an important part.

So What Is Full-Stack?

After understanding frontend and backend, full-stack becomes much easier to understand.

Simply put, a full-stack engineer is someone who can handle both frontend and backend.

If we widen the scene a little, full-stack is like someone who can stand in the front of the restaurant, dare to walk into the kitchen, and even help both sides coordinate their rhythm.

They may be able to:

  • Build frontend pages
  • Integrate APIs
  • Write backend logic
  • Design databases
  • Handle deployment and basic operations

That means they roughly understand the whole chain from the user opening the website to the data actually being stored in the database, and may even be able to implement each part.

Does Full-Stack Mean Being Extremely Strong at Everything?

I also want to be fair to full-stack engineers here.

Many people hear full-stack and imagine a mythical person who maxes out frontend, backend, database, Server, CI/CD, security, UI/UX, and also fixes the office printer at night.

Reality is usually not like that.

A more practical understanding is:

Full-stack does not mean scoring 100 in every subject. It means you understand the overall flow and can solve problems across boundaries.

Some full-stack engineers lean frontend. Some lean backend. Both are normal.

The key is that when a feature needs to connect from the screen all the way to the database, they do not only look at their own small piece. They understand how the whole thing connects.

This is also why many companies like hiring full-stack engineers: communication cost is often lower, and things can move faster.

Of course, the cost is that brain capacity often feels insufficient. Yesterday you were adjusting layout, today you are checking SQL, and tomorrow you may be reading Nginx config. In a way, a full-stack engineer’s daily life is a technically sophisticated kind of split attention.

A Simple Example: Who Does What in a Login Feature?

If we use login as the example, the division between frontend, backend, and full-stack becomes very clear.

Frontend Responsibilities

  • Create the login page
  • Let the user enter account and password
  • Send the data after the login button is clicked
  • After receiving the backend response, decide whether to show success, failure, or an error message
  • Temporarily store login information in the browser after success

Backend Responsibilities

  • Receive the account and password sent from frontend
  • Verify whether the account and password are correct
  • Query the user from the database
  • Determine whether the account status is normal
  • Return login credentials or related information after successful verification

How Would Full-Stack Look at It?

A full-stack engineer usually looks at the whole flow:

  • How to design the frontend page smoothly
  • How to name the API routes reasonably
  • How to define the response format for easier integration
  • How to store the token more safely
  • How to design the table so it is less likely to cause problems

So the value of full-stack is often not “one person doing everything looks cool,” but “one person can more easily understand how the whole system works.”

My Own Understanding in One Sentence

If you just want to quickly grasp the concept, I would summarize it like this:

  • Frontend: Anything related to the screen, browser, user interaction, and browser-side state management is mostly frontend.
  • Backend: Anything related to Server, database, business logic, verification, and data processing is mostly backend.
  • Full-stack: Someone who can connect frontend and backend, understand the whole flow, and solve problems across both sides.

This is not an academic definition, but for most beginners, I think it is enough.

Conclusion: Please Stop Calling Every Engineer “Someone Who Fixes Computers”

Now that I have written this much, I hope the colleague who waited a week for this article can forgive me.

I also hope that other readers will no longer feel that frontend, backend, and full-stack are distant, hard technical terms.

They are not that mysterious.

Frontend is what lets you see, click, and use things.

Backend is what makes all of that truly work, with real data and real logic.

Full-stack means understanding both sides and connecting the whole car from the steering wheel to the engine.

If we look one layer higher, we also encounter Infra.

Infra means Infrastructure, the foundation that lets systems run. In plain language, aside from frontend and backend code, it deals with where the whole system runs, how it connects, how it is deployed, and how it stays stable.

If frontend is like actors on stage and backend is like the team that actually creates the content behind the scenes, Infra is more like the stage crew and control room. The audience may not see them, but if lighting, cables, machines, or timing fail, the entire performance is exposed.

For example:

  • How should Servers be configured?
  • How should Databases be deployed?
  • How should Nginx or a Web Server be configured?
  • How should services be packaged with Docker?
  • How should the network connect?
  • Which Ports should be opened?
  • How should reverse proxy be designed?
  • How should the overall system architecture be planned for stability?

These topics usually extend beyond pure backend because they are no longer just about writing business logic. They require thinking about how the whole service survives, runs smoothly, and lets frontend and backend collaborate reliably.

Honestly, this is also exactly the area I have always been interested in and continue to build experience in.

Although I started from backend, the things I do are not limited to backend. From frontend integration and backend design to deployment, networking, and Infra, I am interested in all of them and keep improving these skills through real practice.

This blog itself is a practical example. If I were only writing articles, things would not have gone this far. But once I wanted to make it a real public website that could keep running, I had to touch frontend, backend, and even some Infra work. The presentation of this site required frontend adjustments, and I also built my own API for page counting. These are not things that can be done by understanding only one technical area.

So if I had to describe myself in one sentence, I would say:

I am not someone who only looks at one technical layer. I am used to looking from frontend and backend all the way to Infra and the overall system.

After all, many problems today cannot be solved by only knowing how to write APIs or only knowing how to build layouts. Very often, the code is written but cannot be deployed; the service is running but the network is unreachable; the feature works, but the architecture starts causing performance or maintenance problems once it grows.

In those moments, people who understand frontend, backend, Infra, networking, and system architecture become especially valuable. They do not see only a single feature. They see how the whole system is built from zero to one, how it is deployed, how it connects, how it runs reliably, and how it truly stays alive.

Especially in the AI era, I increasingly feel that the people who can truly use AI well are often not those who only know how to write prompts, but those who understand the whole system architecture. In the end, what you face is never just the model itself. It includes frontend interaction, backend integration, data flow, service deployment, permission control, cost calculation, and stable system operation.

In that sense, the more we enter the AI era, the more valuable “understanding the whole architecture” becomes. You are not just building a function. You need to put it into the real world so it can be used, maintained, and kept alive over time.

If you are interested in the process of building a service from zero to one and making it real, you can also read my earlier article: Building a Counter API from Scratch: A Simple Side Project with Hidden Complexity. That article shares how I built an API all the way from cloud VM, Docker, Nginx, DNS, SSL, and database setup.

As for whether engineers all know how to fix computers?

Well, that question is a bit like asking whether a chef can repair a gas stove. Some can, but it is really not a required part of the job title.
